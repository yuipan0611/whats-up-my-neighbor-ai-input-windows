# beta.10 實測問題與防止回歸

狀態：beta.11 修復候選，尚未發布，基準 main `6f05dcb`。本文件只記錄已確認程式行為；驗證及發布狀態另列，不將交叉建置當成 Windows 操作驗收。

## 決定與驗收

- #21：單則失敗不得阻擋下一則。保留失敗原文與手動重試，不自動重送。第二則必須可獨立建立嘗試；明確失敗不能顯示「可能已送達」的阻擋確認。重試須沿用原 ID，不能誤送目前編輯的另一段文字。
- #22：逐則「從本機刪除」，不是遠端收回。切換／重開不能復活；不得刪掉其他訊息、對話或正在編輯的新內容。已送出但 ACK 晚到或對方重送時，沿用既有 tombstone 保護。刪除失敗嘗試不得卡住傳送。
- #23：2026-11-05 使用者澄清右鍵改暱稱符合既有操作習慣；保留右鍵入口，不新增按鈕。暱稱是本機聯絡人綽號，不是自己的對外名稱。確認右鍵、鍵盤選單、儲存、切換及重啟，不能因回報標題就推定功能未實作。

## 已確認的程式缺口

- `ChatWindow.Actions.cs#SendCoreAsync` 對所有非 sending 的舊嘗試與不同文字都彈出「可能已送達」確認，包含明確 failed；預設 No 使下一則提前返回。
- `ChatWindow.Ui4.cs#SyncAttemptMessage` 只呈現 inbox 最新的一個失敗嘗試，建立下一則後舊卡消失，雖然資料庫仍保留原文。
- `MessageHistoryView.cs#Build` 的訊息右鍵選單只有複製；沒有逐則刪除儲存與 UI 接線。
- `ChatWindow.ClassRoster.cs#RenameNicknameClick` 已有右鍵與對話框，但儲存 lambda 在 ChatStoreWorker 背景執行緒直接讀取 `input.Text`，違反 WPF Dispatcher 所屬執行緒限制。原生 CI 42020785337 已實際抓到：右鍵與對話框操作通過，儲存後名稱仍為原名。修正為 UI 執行緒先擷取純字串，再交給 worker；snapshot token 與 runtime／關閉檢查保留。

## 影響與實作順序

1. 使用既有 SQLite 交易／刪除 tombstone，新增有對話範圍的逐則刪除與失敗嘗試移除；補真 SQLite 的隔離、重送、晚到 ACK、草稿及重啟測試。
2. 新訊息送出移除舊失敗的阻擋確認；保留失敗卡與原 ID 重試，避免覆蓋另一份編輯內容。接上訊息右鍵刪除並刷新真正儲存結果。
3. Windows 原生隔離測試實際 Send、刪除與右鍵暱稱；全套教室回歸及 WPF 建置後，同一個 PR／候選交付。

高風險處是本機資料刪除與草稿競態，沿用交易、範圍檢查與 epoch。保持 wire、schema、名單身分／IP、核准素材不變。基準 `--classroom-inbox`：161 項通過。

## 修復內容與守門條件

- 移除新訊息被舊失敗／待確認內容攔住的確認視窗。待確認卡仍明示對方可能已收到；只有使用者明確按重試才重送原 ID。
- 失敗嘗試以分頁讀取並保留原文，下一則確認後不會隱藏前一則。重試前核對原 ID／tryCount，避免過期卡重送、連按重送或覆蓋另一份輸入。
- 逐則刪除限指定 conversation＋sequence；失敗卡另核對 tryCount／非 sending。已刪除的 classroom 訊息保留去重墓碑，晚 ACK、重送及附件通知不會復活。附件 metadata／待送回條隨訊息清除；受管理檔案後續沿用附件清理，外部另存檔不動。
- 失敗草稿只在 epoch、revision、原文完全相符且沒有新附件時一起移除。新草稿、新附件與其他對話必須保留；舊 autosave 不可寫回已刪除草稿。
- 等待 ACK 時的新編輯在 own-ACK clear 後必須寫回 classroom 草稿；原路徑誤用 signed/v2 Persist。新增實際 epoch 推進、下一則保存與再次送出的 SQLite 回歸。
- 同時修正 idle classroom 取消誤走 signed/v2 CancelAttempt 的路由，沿用 classroom 狀態與取消文案。取消網路嘗試與刪除本機內容是兩個不同操作。
- 暱稱保留原右鍵／對話選單，未添加新入口。背景工作只接收已擷取的名稱字串，不能讀寫 WPF 控制項；UI 更新必須回到 Dispatcher。以真 SQLite 重啟及 Windows 原生右鍵驗證既有功能。
