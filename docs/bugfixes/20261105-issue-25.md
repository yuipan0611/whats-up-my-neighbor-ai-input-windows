# Issue #25：閱讀後未讀數字未清除

基準：main `6f05dcb`。範圍限前景聊天可視訊息的已讀處理與未讀清單更新。

## 影響與驗證計畫

1. 以 Windows 原生 WPF＋隔離 SQLite 建立兩則未讀，經真正對話清單入口開啟，觀察徽章及本機已讀；先保留修正前結果與診斷。
2. 依重現結果修正 `ChatWindow.Inbox.cs` 的讀取／顯示接線，沿用 `VisibleReadContext`、視窗／分頁／世代與交易保護。非可視訊息、其他對話及關閉回條時的本機已讀均需維持正確。
3. 驗證開啟、背景、切換、部分可視、接收新訊息與重新開啟 SQLite。執行 inbox workspace／classroom-all 回歸、WPF 建置與 Windows 原生 smoke；不以交叉建置代替原生結果。

風險中等：WPF 可視範圍與非同步資料更新會影響本機已讀及對外回條。保持 schema、wire、名單身分、附件、核准素材與傳送行為不變。測試只用合成資料及 loopback，不存取日常 profile。

基準 `--inbox-workspace`：25 項通過。既有 safety config strict validation 通過，既有雙 Windows／教室／IME／實體 DPI 限制仍適用。

## 根因與修正

使用者確認發生版本為 beta.10。單純的兩則短訊息案例在套件與單一 EXE 均通過，因此另以儲存延遲與實際視窗變更重現時序：

1. 可視已讀檢查 A 等待 ChatStoreWorker，`_readBusy=true`。
2. 視窗／捲動更新令 view generation 過期，並排程新的檢查 B。
3. B 的 timer 觸發後先 Stop，但舊程式因 `_readBusy` 直接返回，丟掉最新畫面的檢查。
4. A 隨後被既有 stale-view 保護拒絕；即使訊息可見，已沒有後續檢查，未讀徽章持續保留。

[修正前原生重現](https://github.com/yuipan0611/whats-up-my-neighbor-ai-input-windows/actions/runs/42029525744)（`8860e5e`）在第 11 項等待「stale busy-worker read 之後的最新畫面已讀」逾時。JSON 確認 active=true、visible=true、historyLoaded=true、readBusy=false、設定關閉，三則訊息均有容器，最新一則仍未讀。初始兩則短訊息的 7 項檢查先行通過；不能將本問題籠統歸因為全部已讀功能未實作。

修正限 `MarkViewportAsync`：遇到忙碌中的讀取時，透過既有 180ms timer 保留最新畫面的檢查，待 worker 恢復後重新擷取目前可視列。仍沿用相同的 foreground／user-opened／pane／geometry／generation／SQLite transaction guards。沒有直接將整個對話歸零，沒有放寬舊畫面的寫入保護。

## 防止回歸

原生 `--unread-smoke-test <隔離目錄>` 使用真 WPF／SQLite；不直接呼叫標記已讀，不注入已讀結果。

- 側欄兩則未讀（classroom＋legacy）、未開啟的自動預覽、實際 Enter 開啟、徽章與總數、其他對話隔離。
- 真正 worker 被延遲時，實際 resize 使舊讀取過期；視窗恢復後須自己消除未讀，不能要求再次點擊。
- 隱藏時的新訊息、ShowChat 重開同一對話、關閉對外回條時的本機已讀。
- 長對話只讀可見訊息，捲動較早訊息後持續扣除，重開 runtime／SQLite 保留結果。

Windows CI 的快速 Native unread regression 與既有完整 Lite workflow（套件＋單一 EXE）均執行相同原生檢查；失敗時保存 JSON、WPF 截圖及合成資料庫。
