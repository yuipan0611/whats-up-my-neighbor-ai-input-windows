# 封鎖（BK）

決策：D-29（使用者勾選「封鎖」，併入第 1 批）、D-30（隱藏本機封鎖行為，傳送端正常成功）。只在本機過濾，不改線上協定；對方不會收到「你被封鎖」的通知。

**BK-01 封鎖聯絡人** 【WPF】
- Given 聯絡人 A（或名單外 IP A）
- When 在聯絡人選單選「封鎖」並確認「封鎖後不再接收 A 的訊息與檔案；A 不會收到通知；可隨時解除」
- Then A 從一般清單移到「已封鎖」區；歷史保留、唯讀

**BK-02 被封鎖者的訊息不收**
- Given A 已封鎖
- When A 傳來文字、貼圖、附件 offer 或已讀回條
- Then 不存入、不通知、不觸發 CT-01 自動加入、不計入未讀；對合法且接收服務仍有效的請求，回應與正常接收無法區分，不改 frozen wire 格式
- And classroom 文字／貼圖回正常 `message.ack status=stored`，以原文、reaction、messageId 計算正常 `content_sha256`；重送同 id 仍回 stored，不保留去重或黑名單。A 的待送完成並停止自動重試；本版 classroom 歷史成功文案為「已送出」，已讀仍需真正的回條
- And legacy v1 沿用既有 HTTP 200 `{"status":"delivered"}`，A 顯示「舊版・已送出」；v1 格式沒有 message.ack／content_sha256，不加入不相容欄位
- And 回條回既有 `receipt.ack status=discarded`，不觸發 ReceiptStored；不送對外已讀回條。封鎖時移除尚未送出的回條，發送前及 hello 後重查封鎖；已經飛出的位元組不能撤回
- And 附件 offer 通過正常格式／session／metadata 驗證後，在接收交易內拒絕落盤，但回現有 `status=offered`（非 complete／cleared）；A 顯示「通知已送出 · 等待收件確認」，offer 待送完成、不自動重試。B 不存 offer metadata、不下載、不發 complete；A 不會顯示「附件已送達」。chunk／complete 存取仍拒絕
- And 不因此產生診斷以外的任何持久紀錄（包含 IP／messageId／正文／附件 metadata／去重列）；診斷只記固定碼，不含 IP 或 messageId。協定回應及必要的短期 RAM session 仍可含既有回音欄位，不落盤。正常驗證失敗、服務停止、資料庫不可用仍依原規則處理，不捏造成功

**BK-03 封鎖不影響課堂檔案以外的別人**
- Given A 已封鎖
- Then 其他聯絡人收發不受影響；A 分享到課堂檔案的檔案在本機不顯示、不自動下載，也不從 A 節點下載（老師節點或其他同學節點的備援副本仍可用）
- And B 封鎖 A 後，B 已持有的 A 署名課堂檔案位元組仍可轉供給其他未封鎖、具既有節點資格的同學；封鎖只影響 B 自己看不看得到、從不從 A 節點取，不減少全班備援。僅對外 status/chunk 查詢略過作者隱藏，來源資格／grant token／位元組範圍／ready／有效 signed 撤下仍必須驗證，不能繼續提供已撤下的檔案

**BK-04 封鎖時待送給 A 的訊息**
- Given 有尚未送達 A 的待送訊息
- When 封鎖 A
- Then 這些待送停止重試並標示「已停止（已封鎖）」，不刪除，解除封鎖後可手動重送

**BK-05 解除封鎖**
- Given A 已封鎖
- When 選「解除封鎖」
- Then A 回到一般清單，沿用原本的備註與歷史；封鎖期間 A 收到成功回應的訊息，本機沒有保存，不主動補回，A 不再自動重試
- And 如果解除後 A 明確以同一 messageId 重新發起傳送，照 CT-01／CT-07 規則正常收訊及歸戶：沒有黑名單，所以不能辨認該 id 曾在封鎖期間被丟棄。D-30 明確接受此界線

**BK-06 封鎖和移除不同**
- 移除聯絡人（CT-13）：對方再來訊會依 CT-07 回到清單
- 封鎖：對方來訊一律不收，直到解除
- Then 兩個操作的文字、確認視窗與清單分區不混用

**BK-07 封鎖老師**
- Given 老師 T
- When 封鎖 T
- Then 先確認「這會取消 T 的老師身分」，封鎖後依 TC-04 取消老師，「＋ 加入老師」重新出現

**BK-08 升級與並行**
- 封鎖清單存在 SQLite 新表（隨第 1 批 migration）；與接收交易在同一交易內判斷，封鎖操作與同時到達的訊息不會出現「封鎖後仍存入一則」的競態
- And v15 實際 DDL 已套用、同交易資料已局部修改後若失敗，整個 migration 回滾到有效 v14，schema/user_version/全部資料表內容不變；保留升級前備份，下次正常開啟可重試並成功升級

## Core 邊界（S0 補齊）

- 採新增 v15，保留已審查與提交的 v14；升級前沿用既有備份。封鎖是固定 IP 的本機規則，不是已驗證的人。這只是本機行為隱藏，不是防偽；換 IP 即可繞過，和 CM-06 的 IP 信任界線相同。封鎖中不可改該聯絡人的 IP／設為老師；須先解除。
- 接收與封鎖依 SQLite writer 交易順序線性化：封鎖提交前已提交的訊息保留；封鎖提交後不新增正文／附件／回條／自動聯絡人。已飛出的網路封包不能撤回。
- BK-03：本機隱藏被封鎖 IP 署名的課堂檔案；其他作者檔案若 A 是副本節點，仍可由未封鎖節點取得。同步自別人的 signed operation 可保留以維持撤下／去重，不能由本機封鎖破壞全班 catalog。
- BK-05：本機不保留被丟棄內容或 messageId 黑名單，也不主動補收；解除後對方重新發起傳送可收到，無法在不記錄丟棄 id／不改協定下永久識別先前遭拒收的 id。
- BK-04：解除不自動恢復 cancelled 待送；使用者必須明確重送。已送回條／已另存檔案無法撤回。
- F4 裁決：儲存體無法判斷來源是否封鎖時，診斷採 fail-closed，不帶訊息 UUID 或來源 IP；仍保留固定錯誤分類，不為了關聯訊息而洩漏識別資訊。此裁決不把資料庫錯誤偽裝成成功收訊。

## D-30 驗證界線

- --blocking 同時驗證正常儲存 ACK 的原文／reaction hash、重送、legacy delivered、receipt discarded、同 id 解除後正常收、固定 IP 公開 API 的 CT 歸戶，以及 B 各資料表列數完全不變／無通知／診斷匯出無 IP、id、檔名或正文。
- 真 TCP／SQLite 雙端自動化在隔離 loopback 執行；產品聯絡人仍拒絕 loopback。測試先用公開 API 建私人 IP 封鎖，再只在測試 DB 把這筆明確操作映射為 loopback；另斷言產品拒絕 loopback，沒有為測試放寬產品規則。此 fixture 證明協定／持久重試／本機零資料，不能代替雙實機或 WPF 驗收。
